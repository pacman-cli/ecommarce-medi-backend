⚡ Optimize LowStockScheduler by filtering in database

💡 What: Added a custom JPQL query `@Query` in `ProductRepository` to filter low stock products directly in the database, and refactored `LowStockScheduler` to use this new method instead of `findAll()` and in-memory filtering.
🎯 Why: Previously, the scheduler loaded all products into memory and iterated through them to find those with low stock. This is highly inefficient (excessive CPU, memory allocation, and GC overhead) and scales poorly as the number of products grows. By delegating the filtering to the database, we significantly reduce memory footprint and execution time.
📊 Measured Improvement: Created a performance test `LowStockSchedulerPerformanceTest` with 50,000 products (10% low stock). Baseline time using `findAll()` was ~1064ms. After optimization, execution time dropped to ~622ms. A clear speedup of roughly 40% in execution time (along with substantial but unmeasured memory savings).
